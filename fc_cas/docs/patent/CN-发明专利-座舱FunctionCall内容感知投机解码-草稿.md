## 说明书

### 技术领域

本发明属于人工智能推理加速与车载智能座舱人机交互技术领域，具体涉及大语言模型在标准 JSON Function Call（工具调用）输出格式下的投机解码（speculative decoding）方法，以及相应的装置、电子设备与计算机可读存储介质。

### 背景技术

车载座舱语音助手广泛采用「大模型 + Function Call」架构：模型在候选工具集合上决定是否调用函数，并以结构化 JSON 表达函数名与参数；执行结果再回填对话。该类输出在产业实践中普遍遵循 OpenAI 兼容的消息协议，即 assistant 消息可携带 `tool_calls` 数组，其中每个元素包含 `type`、`function.name`、`function.arguments`（arguments 为 JSON 对象的字符串序列化）等字段，并配套提供 `tools` 侧的 JSON Schema（含 `properties`、`enum`、`required` 等）。

大模型自回归解码延迟高。投机解码通过草稿模型提出多 token 候选、目标模型并行验证，可实现无损加速。公开技术已涵盖复用目标内部表示的草稿、块并行草稿、半自回归修正与置信度调度等。

然而，座舱 Function Call 场景具有鲜明的输出结构异质性：

1. **工具调用区段**：序列化后的 JSON 骨架（字段名、括号、引号、逗号）及大量 **enum 约束参数** 熵极低，草稿极易被接受；  
2. **自然语言回复区段**：拒识话术、澄清、闲聊等高熵文本，过长草稿易被拒绝；  
3. **参数自由字符串槽位**（如歌名、POI、手册主题）介于二者之间。

现有投机解码多采用全局统一的草稿长度与置信度阈值，或仅做逐 token 置信度截断，**未显式利用标准 JSON Function Call 的区段边界与 tools Schema**，导致结构化区段加速潜力未吃满、自然语言区段无效验证开销偏大。

### 发明内容

#### 要解决的技术问题

在目标模型输出遵循标准 JSON Function Call 协议的前提下，如何识别自然语言区段与工具调用区段（及工具调用内部的骨架 / 枚举槽 / 自由字符串槽），并差异化配置投机草稿策略，以提升平均接受长度与端到端加速比，同时保持与目标模型验证机制相容。

#### 技术方案

本发明提供一种区段感知投机解码方法，包括：

**（A）区段识别**  
在解码过程中维护输出区段状态机，至少区分：

- `NL`：自然语言回复；  
- `TOOL_SKELETON`：Function Call JSON 骨架与确定性语法片段；  
- `TOOL_ENUM`：Schema 中声明为枚举的参数值位置；  
- `TOOL_FREE`：Schema 中未枚举约束的自由字符串 / 数值等槽位；  
- （可选）`TOOL_RESULT`：tool 角色回传内容区段。

区段识别优先采用与标准协议一致的判定信号，包括但不限于：特殊控制标记、增量 JSON 语法状态（键名 / 字符串值 / 结构符号）、以及当前 `function.name` 对应 tools Schema 的指针位置。

**（B）分区策略调度**  
按区段类型查表得到投机策略 \(\pi(r)\)，至少配置：最大草稿长度 \(B(r)\)、置信度截断阈值 \(\theta(r)\)；可选配置是否启用 Schema 约束采样、是否对确定性片段做模板注入。

典型配置（可标定）：

| 区段 \(r\) | \(B(r)\) | \(\theta(r)\) | 草稿模式 |
|-----------|----------|---------------|---------|
| NL | 小 | 高（保守） | 普通草稿 |
| TOOL_SKELETON | 大 | 低（激进） | 模板注入优先 |
| TOOL_ENUM | 大 | 低 | Schema 枚举约束采样 |
| TOOL_FREE | 中 | 中 | 普通 / 半自回归草稿 |

**（C）草稿生成与目标验证**  
在目标模型条件特征（如选定层隐藏状态）下，由草稿模块按 \(\pi(r)\) 生成候选；若存在置信度头，则在区段阈值 \(\theta(r)\) 下截断候选前缀；目标模型并行验证并接受最长合法前缀；更新区段状态机。

**（D）领域数据驱动的草稿训练与评测（可后补实验）**  
使用座舱标准 FC 数据集（见最佳实施例所依据的数据组织方式）构建训练语料与目标缓存，训练领域草稿模型；在测试划分上统计分区域接受长度与加速比。

#### 有益效果

1. 将投机调度从「全局超参」提升为「与标准 FC 协议对齐的区段调度」，结构性吃满低熵 JSON 加速红利；  
2. 借助 tools Schema，在枚举槽位显著提高草稿命中率，缩短舱内时延；  
3. 与置信度头兼容，形成「区段基线 + token 级截断」两级自适应；  
4. 不改变目标模型验证角色时，可保持与目标分布一致的无损加速路径。

### 具体实施方式

#### 最佳实施例所依据的数据组织（processed_FC_dataset）

本实施例所对接的座舱 Function Call 数据采用标准消息协议，单条样本字段至少包括：

- `id`：样本标识；  
- `messages`：对话消息列表，角色含 `user` / `assistant` / `tool`；  
- `tools`：本轮候选工具列表（OpenAI 风格），每项含 `type: "function"` 以及 `function.name`、`function.description`、`function.parameters`（JSON Schema，含 `properties` / `enum` / `required` 等）；  
- 可选元数据：`source`、`conversation_id`、`turn` 等。

其中，assistant 消息在需要调用工具时，`content` 可为空，并携带 `tool_calls` 数组；每个 tool call 形如：

```json
{
  "id": "call_xxx",
  "type": "function",
  "function": {
    "name": "ota_update",
    "arguments": "{\"action\": \"check_update\"}"
  }
}
```

`arguments` 为 **JSON 对象的字符串**。候选工具数量通常为每轮 3～5 个；工具覆盖音乐、空调、导航、OTA、ADAS、座舱设置等车载域能力；参数 Schema 中大量字段带 `enum`，同时存在歌名、主题等自由字符串槽位。数据可划分为 train / validation / test，用于草稿训练与加速评测。

> 说明：上述数据组织用于支撑可实施性与评测协议；权利要求保护的是方法本身，不将某一具体数据集权利化。

#### 实施例 1：基于标准 FC 序列化的区段状态机

**S1** 加载经座舱 FC 任务微调的目标语言模型 \(M_q\)，及条件于 \(M_q\) 内部特征的草稿模型 \(M_p\)。

**S2** 将目标输出侧的生成过程与聊天模板对齐。当模型进入 tool call 序列化路径时，区段识别器根据已生成前缀判定：

1. 若处于自然语言文本（无 tool_calls 结构符号 / 标记）→ `NL`；  
2. 若处于 JSON 结构符号、固定键名（如 `"name"`、`"arguments"`）、函数名已由 Schema 候选集合约束的位置 → `TOOL_SKELETON`；  
3. 若当前 JSON 指针落在某一 `properties.field` 且该字段声明 `enum` → `TOOL_ENUM`；  
4. 若落在无 enum 的 string / number 等槽位 → `TOOL_FREE`。

实现上可采用增量 JSON 解析器维护指针，并在函数名确定后绑定对应 tools Schema。

**S3** 查表得到 \(\pi(r)=(B(r),\theta(r),\text{mode}(r))\)。

**S4** \(M_p\) 按模式生成至多 \(B(r)\) 个候选 token；若启用置信度头，将候选截断到第一个 \(\sigma(c_i)<\theta(r)\) 的位置。

**S5** \(M_q\) 并行验证，接受最长正确前缀；更新解析器状态与区段；循环至结束符或停止条件。

#### 实施例 2：Schema 约束与模板注入（强化加速）

当区段为 `TOOL_SKELETON` 时：对确定性片段（结构符号、Schema 键名、必需的 JSON 标点）优先**模板注入**，减少模型采样步。

当区段为 `TOOL_ENUM` 时：将采样空间限制为该字段 enum 集合（非法 token logits 置为极小值），草稿几乎必然命中短枚举值（例如 `"check_update"`、`"play_song"`）。

当区段为 `TOOL_FREE` 时：回退普通草稿，并可适当减小 \(B(r)\) 或提高 \(\theta(r)\)。

目标模型仍执行验证；在「仅约束草稿、验证不放宽」的配置下，保持无损加速语义。

#### 实施例 3：领域草稿训练与评测协议（实验可后补）

**训练**  
1. 自 train 划分读取 `messages` + `tools`；  
2. 用目标模型按部署聊天模板生成 / 对齐 assistant 输出，写入训练序列；  
3. 抽取目标模型指定层隐藏状态形成 target cache；  
4. 按块级并行目标训练草稿模型（可复用公开的块草稿训练框架作为实现载体，本专利不主张该训练框架本身）。

**评测（待补数值）**  
在 test 划分上对比：

- 基线 A：全局固定 \(B,\theta\) 的投机解码；  
- 基线 B：仅置信度截断、无区段策略；  
- 本发明：区段策略 ± Schema 约束。

指标建议：

| 指标 | 含义 |
|------|------|
| \(\tau\) | 平均接受长度 |
| \(\tau_{\text{NL}},\tau_{\text{TOOL}}\) | 分区域接受长度 |
| Speedup | 相对自回归的加速比 |
| P50/P99 时延 | 舱内体验相关 |
| 工具名 / 参数准确率 | 确认无损验证下任务正确性不变 |

申请人声明：本申请提交时可无完整实验数值；获授权过程中或分案/补正时可依据同一 `processed_FC_dataset` 协议补强实施例数据。

#### 实施例 4：装置与设备

一种区段感知投机解码装置，包括：FC 区段识别模块、策略调度模块、Schema 约束模块、草稿生成模块、目标验证模块。  
一种电子设备（座舱域控制器、车机主机或云侧推理节点），包括处理器与存储器，执行上述方法。  
一种计算机可读存储介质，存储实现上述方法的程序。

## 摘要

本发明公开一种面向标准 JSON Function Call 的区段感知投机解码方法及装置。该方法在解码过程中识别自然语言回复区段与工具调用结构化区段，并按区段差异化配置草稿长度与置信度阈值；进一步可结合 tools 的 JSON Schema，对 JSON 骨架与枚举参数分别进行模板注入与枚举约束采样，再由目标模型验证接受。本发明适用于车载座舱等 Function Call 密集场景，能够提升结构化输出区段的接受长度与推理加速比。

## 内部设计备忘（勿提交专利局）

### 为何如此切保护重心

| 选项 | 评价 | 结论 |
|------|------|------|
| 仅「分区 block/阈值」 | 有新意，但易被「自适应阈值」类公开技术靠近 | 作独立权利要求主干，必须写清「针对 FC 区段且 TOOL 更激进」 |
| 仅「schema 约束解码」 | 约束解码本身已有较多公开 | 不单独作最独权，作从属强化 |
| **区段调度 + Schema 槽位分化（骨架/枚举/自由）** | 与 `processed_FC_dataset` 高度同构：tc_only 为主、enum 密集、arguments 短 | **采纳为保护组合** |

### 数据集支撑点（评测可直接用）

- 规模：train 7105 / val 875 / test 917（总计 8897）  
- assistant 模式：tc_only 为主，另有 NL 拒识等，天然适合分区域统计 \(\tau_{\text{NL}}\) vs \(\tau_{\text{TOOL}}\)  
- 35 个座舱工具；每轮 3～5 候选 tools；arguments 长度中位约 26 字符 → 骨架+枚举加速收益预期高  
- 标准字段：`messages` + `tools` + `tool_calls` + `function.arguments` 字符串

1. 全局 DSpark 式固定策略；  
2. 本发明：仅 NL/TOOL 两区调度；  
3. 本发明 + enum/骨架约束。
